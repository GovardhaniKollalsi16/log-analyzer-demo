# incident-app-config (v0.2)

> Part of the `incident-logs` investigation. Read that coordinator's hard rules first; they apply here.
> Samples below are **real `mocklogs` output** rendered from a **neutral fixture** (all names `example-*`, benign lines only), so they match the real formats but hint at no scenario. They're generated by `python -m mocklogs.skill_samples --write`; don't edit them by hand. A test fails if they drift.

## 1. Logging in

- Config is read with the **user's SSO session**. **You never run `mocklogs sso login`.**
- SSO missing or expired (exit code **3**): stop, ask the user to run `mocklogs sso login`, and retry **once**. If the user declines → record `auth_required`.
- Not entitled (exit code **4**):
  <!-- mocklogs-sample: app-config/forbidden -->
  ```
  $ mocklogs kubectl get configmap example-downstream-config --context example-cluster -n apps -o json
  # MOCK DATA — synthetic, not from any real system
  Error from server (Forbidden): configmaps "example-downstream-config" is forbidden: user "mock-user" cannot get resource "configmaps" in namespace "apps" on cluster "example-cluster"
  # exit code 4
  ```
  <!-- /mocklogs-sample -->
  Record `access_denied`. **This matters:** without the config, you can't tell which incident topics the app consumes vs. produces, you don't know its upstream/downstream apps or their Kafka client IDs (so step 4 becomes `missing_input`), and you can't check its limits. That lowers the confidence you may claim. Say so explicitly in the report. (Kafka and DB access don't depend on it: their inputs come from the incident.)
- The configmap, namespace or cluster doesn't exist (exit code **5**):
  <!-- mocklogs-sample: app-config/not-found -->
  ```
  $ mocklogs kubectl get configmap example-missing-config --context example-cluster -n apps -o json
  # MOCK DATA — synthetic, not from any real system
  Error from server (NotFound): configmaps "example-missing-config" not found
  # exit code 5
  ```
  <!-- /mocklogs-sample -->
  **Don't retry, and don't try a different value.** The input you were given (from the incident) is wrong or stale. Record `not_found` naming the exact input that failed, and continue. Never substitute a guessed name, cluster or host.

## 2. Required inputs

| Input | Required? | Where it must come from |
|---|---|---|
| `cluster` | **Required** | The incident's `app: cluster=` line |
| `namespace` | **Required** | The incident's `app: namespace=` line |
| `app` | **Required** | The seed line's `app` (seed app only) |

**If any required input is missing, don't run any command from this skill.** Record a `missing_input` gap that names what's missing (e.g. `missing_input: app namespace`) and continue with the next step. Never guess or substitute a value, and never reuse another app's or another source's value.

Fetch config for the **seed app only**. Never for upstream or downstream apps.

## 3. Command
```
mocklogs kubectl get configmap <app>-config --context <cluster> -n <namespace> -o json --save-dir <workdir>
```
Config has no time dimension: it's the current config. There is no change history, so don't reason about *when* a value changed.

## 5. What to read from it

**Config is never a source of access inputs.** The Kafka cluster and topics and the DB host and name come from the **incident** (no input, no access). The config is used for:

| Key | Used for |
|---|---|
| `kafka.consumer.topics` | Which incident topics the app **consumes** → the producers on them are **upstream** |
| `kafka.producer.topics` | Which incident topics the app **produces** → the consumers of them are **downstream** |
| `kafka.consumer.group` | The group for the lag check, if the incident gave no `group=` |
| `kafka.consumer.client.id` / `kafka.producer.client.id` | The seed app's **own** Kafka client IDs, which identify its lines in Kafka client logs and its row in lag tables |
| `upstream.apps` / `downstream.apps` | **The** list of related apps for step 4. The only source; never infer apps from Kafka output |
| `upstream.<app>.kafka.client.ids` / `downstream.<app>.kafka.client.ids` | Which Kafka client IDs belong to which related app. This is how a `clientId=` in Kafka logs or a `CLIENT-ID` in a lag table is attributed to an app. An ID that isn't listed stays unattributed |
| timeouts, retries, pool sizes, thread counts | Limits that `investigator` checks for inconsistencies (e.g. pool size below worker threads, retries × timeout longer than a consumer can wait). You don't judge these yourself |

Topics in the config that **aren't** in the incident are **not** fetched (no input, no access). The config may also name a Kafka cluster or DB that differs from the incident. Don't use the config's value. Note the mismatch in the report.
