# incident-app-logs (v0.3)

> Part of the `incident-logs` investigation. Read that coordinator's hard rules first; they apply here.
> Samples below are **real `mocklogs` output** rendered from a **neutral fixture** (all names `example-*`, benign lines only), so they match the real formats but hint at no scenario. They're generated by `python -m mocklogs.skill_samples --write`; don't edit them by hand. A test fails if they drift.

## 1. Logging in

- There are no agent credentials. App logs are read with the **user's SSO session**. **You never run `mocklogs sso login`**; the user does.
- If the session is missing or expired (exit code **3**):
  <!-- mocklogs-sample: app-logs/sso -->
  ```
  $ mocklogs kubectl logs deploy/example-app --context example-cluster -n apps --timestamps
  # MOCK DATA — synthetic, not from any real system
  error: SSO session expired or missing. Ask the user to run: mocklogs sso login
  # exit code 3
  ```
  <!-- /mocklogs-sample -->
  Stop and ask the user to log in, then retry the same command **once**. If the user declines → record `auth_required` for this app and continue.
- If the user isn't entitled to this app's logs (exit code **4**):
  <!-- mocklogs-sample: app-logs/forbidden -->
  ```
  $ mocklogs kubectl logs deploy/example-app --context example-cluster -n apps --timestamps
  # MOCK DATA — synthetic, not from any real system
  Error from server (Forbidden): pods is forbidden: user "mock-user" cannot get logs for deployment "example-app" in namespace "apps" on cluster "example-cluster"
  # exit code 4
  ```
  <!-- /mocklogs-sample -->
  Record `access_denied` for this app. Don't retry.
- The app, namespace or cluster doesn't exist (exit code **5**):
  <!-- mocklogs-sample: app-logs/not-found -->
  ```
  $ mocklogs kubectl logs deploy/example-missing --context example-cluster -n apps --timestamps
  # MOCK DATA — synthetic, not from any real system
  Error from server (NotFound): deployments.apps "example-missing" not found
  # exit code 5
  ```
  <!-- /mocklogs-sample -->
  **Don't retry, and don't try a different value.** The input you were given (from the incident) is wrong or stale. Record `not_found` naming the exact input that failed, and continue. Never substitute a guessed name, cluster or host.

## 2. Required inputs

| Input | Required? | Where it must come from |
|---|---|---|
| `cluster` (kube context) | **Required** | Seed app: the incident's `app:` line. Related app: the incident's `app[<name>]:` line |
| `namespace` | **Required** | Same as `cluster` |
| `app` | **Required** | Seed app: the seed line's `app`. Related apps: the names the **seed app's config** declares in `upstream.apps` / `downstream.apps`. Never an app name derived from a client ID or pod name |
| time window | **Required** | Derived from the seed line's `ts` (default −10 min / +2 min) |
| business key (`order_id`, `product_id`, …) | **Required for related apps** | Chosen from the seed record by the coordinator's correlation-key table (§3). Its value is the seed record's field of that name. Without it, related apps' logs aren't fetched (`missing_input: business key`) |
| `correlation_id` | Optional, **this app only** | Seed app: the seed line. Related app: the `correlation_id` on that app's **own** lines returned by the business-key search (or the Kafka header, if that app is the producer). Never use one app's correlation ID to search another app |
| `instance` + `thread` | Optional (both or neither) | The seed line. Only for the **seed app's** own thread segment |

**If any required input is missing, don't run any command from this skill.** Record a `missing_input` gap that names what's missing (e.g. `missing_input: app cluster`) and continue with the next step. Never guess or substitute a value, and never reuse another app's or another source's value.

**Related apps need their own location.** Use an `app[<name>]: cluster=… namespace=…` line from the incident for that app. If the incident has no such line, record `missing_input: cluster/namespace for <name>` and **don't fetch** that app's logs. Never reuse the seed app's cluster for another app.

## 3. Commands

**Search by time + business key** (across apps: the first search for a **related** app):
```
mocklogs kubectl logs deploy/<app> --context <cluster> -n <namespace> --timestamps \
    --since-time=<rfc3339> --until-time=<rfc3339> \
    --grep <business-key-value> --save-dir <workdir>
```

**Search by time + that app's own correlation ID** (within one app: the seed app's first search, and a related app's second search):
```
mocklogs kubectl logs deploy/<app> --context <cluster> -n <namespace> --timestamps \
    --since-time=<rfc3339> --until-time=<rfc3339> \
    --grep <correlation-id> --save-dir <workdir>
```

**Search by time + thread** (the seed's thread segment: ID-less lines from the same unit of work, such as retries and stack traces):
```
mocklogs kubectl logs deploy/<app> --context <cluster> -n <namespace> --timestamps \
    --since-time=<rfc3339> --until-time=<rfc3339> \
    --instance <pod> --thread <thread> --save-dir <workdir>
```

**Search by time only** (when the seed has no correlation ID, or the narrower searches found nothing):
```
mocklogs kubectl logs deploy/<app> --context <cluster> -n <namespace> --timestamps \
    --since-time=<rfc3339> --until-time=<rfc3339> --save-dir <workdir>
```

Notes:
- `--since-time` / `--until-time` are RFC 3339 UTC, e.g. `2026-01-01T00:00:00Z`.
- `--grep` and `--until-time` are **mock extensions** (the real tool would need a pipe, which isn't allowed).
- **Thread names are only meaningful within one app on one instance.** Never compare thread names across apps or pods. `investigator` limits thread links to a 1-minute window and stops them at a different correlation ID.

## 4. Output format

The first line is the MOCK banner. Then each line is an RFC 3339 prefix followed by one JSON object:
<!-- mocklogs-sample: app-logs/output -->
```
$ mocklogs kubectl logs deploy/example-gateway --context example-cluster -n apps --timestamps --since-time=2026-03-14T09:00:00Z --until-time=2026-03-14T09:00:25Z
# MOCK DATA — synthetic, not from any real system
2026-03-14T09:00:01.977097000Z {"ts":"2026-03-14T09:00:01.977Z","level":"INFO","cluster":"example-cluster","namespace":"apps","app":"example-gateway","instance":"example-gateway-c773c-0","thread":"health-1","logger":"app.Health","msg":"Health check OK"}
2026-03-14T09:00:20.000000000Z {"ts":"2026-03-14T09:00:20.000Z","level":"INFO","cluster":"example-cluster","namespace":"apps","app":"example-gateway","instance":"example-gateway-c773c-0","thread":"http-nio-8080-exec-1","logger":"gateway.OrderAccessLog","correlation_id":"c-630735","order_id":"o-1000","msg":"POST /v1/orders -> 202 Accepted"}
# exit code 0
```
<!-- /mocklogs-sample -->
Fields: `ts`, `level`, `cluster`, `namespace`, `app`, `instance`, `thread`, `logger`, `correlation_id` (this app's own; may be missing), business keys such as `order_id` / `product_id` (when the code logs them), `msg`, optional `error{type, message, stack}`.

Kafka **client** activity (producer sends, consumer processing) is logged here too, under a `logger` naming the Kafka client.

## 5. What to look for

You don't classify (`investigator` does). These signals just help you choose filters and decide whether to widen the window:
- `level` ERROR/FATAL, or an `error` object with a stack trace;
- retry wording ("retrying", "attempt n/N", "retries exhausted", "giving up");
- timeouts and waits that expire;
- Kafka client warnings and errors under a Kafka-client `logger`;
- circuit breaker opened, thread pool or queue saturation;
- the **first** error for the correlation ID, and what the same thread logged just before it.

For a related app: search by the business key first, then by the `correlation_id` found on its returned lines, to get that app's whole unit of work. If a correlation-ID search returns only the seed line, run the thread search next. If both are empty, widen the window once before moving on.
