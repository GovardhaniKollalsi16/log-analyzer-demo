# incident-kafka (v0.4)

> Part of the `incident-logs` investigation. Read that coordinator's hard rules first; they apply here.
> Samples below are **real `mocklogs` output** rendered from a **neutral fixture** (all names `example-*`, benign lines only), so they match the real formats but hint at no scenario. They're generated by `python -m mocklogs.skill_samples --write`; don't edit them by hand. A test fails if they drift.

## 1. Logging in

- Kafka is read with the **user's SSO session**. There are no agent credentials, and **you never run `mocklogs sso login`**.
- SSO missing or expired (exit code **3**):
  <!-- mocklogs-sample: kafka/sso -->
  ```
  $ mocklogs kafka-get-offsets --bootstrap-server example-kafka:9092 --topic example.in --time -1
  # MOCK DATA — synthetic, not from any real system
  error: SSO session expired or missing. Ask the user to run: mocklogs sso login
  # exit code 3
  ```
  <!-- /mocklogs-sample -->
  Stop, ask the user, and retry **once**. If the user declines → record `auth_required` for the remaining Kafka steps.
- Not authorized for a topic or group (exit code **4**):
  <!-- mocklogs-sample: kafka/forbidden -->
  ```
  $ mocklogs kafka-get-offsets --bootstrap-server example-kafka:9092 --topic example.in --time -1
  # MOCK DATA — synthetic, not from any real system
  org.apache.kafka.common.errors.TopicAuthorizationException: Not authorized to access topics: [example.in]
  # exit code 4
  ```
  <!-- /mocklogs-sample -->
  Record `access_denied` for that topic or group. Don't retry.
- The Kafka cluster is unreachable, or the topic or group doesn't exist (exit code **5**):
  <!-- mocklogs-sample: kafka/unreachable -->
  ```
  $ mocklogs kafka-get-offsets --bootstrap-server example-other:9092 --topic example.in --time -1
  # MOCK DATA — synthetic, not from any real system
  Error: Timed out waiting for a node assignment (bootstrap example-other:9092).
  # exit code 5
  ```
  <!-- /mocklogs-sample -->
  **Don't retry, and don't try a different value.** The input you were given (from the incident) is wrong or stale. Record `not_found` naming the exact input that failed, and continue. Never substitute a guessed name, cluster or host.

## 2. Required inputs

| Input | Required? | Where it must come from |
|---|---|---|
| Kafka cluster = `--bootstrap-server` | **Required** for every command | The incident's `kafka: bootstrap=` line |
| `topic` | **Required** for message, offset and log commands | The incident's `kafka: topics=` line. **Only those topics** |
| time window | **Required** for offset and log commands | Derived from the seed line's `ts` |
| business key (`order_id`, `product_id`, …) | **Required** for the message search | Chosen by the coordinator's correlation-key table (§3) from the seed record. Kafka stores it in the message **value** field of the same name. Without it, record `missing_input: business key` for the message search (the client and broker logs are still collected) |

**If any required input is missing, don't run any command from this skill.** Record a `missing_input` gap that names what's missing (e.g. `missing_input: kafka bootstrap`) and continue with the next step. Never guess or substitute a value, and never reuse another app's or another source's value.
If the cluster is present but a particular command's extra input is missing (e.g. no `group`), skip **only that command** and record which input was missing.

**Which apps are upstream/downstream, and which client IDs are theirs, comes only from the seed app's config** (`upstream.apps`, `downstream.apps`, `*.kafka.client.ids`; see `incident-app-config`). **Never derive an app from a client ID's text**: `example-upstream-producer-1` is just an ID until the config maps it. Topic direction (consume vs. produce) also comes from the config (`kafka.consumer.topics` / `kafka.producer.topics`). Without the config, upstream/downstream apps are **unknown**: record `missing_input: upstream/downstream apps` and report the topics' direction as unknown. Each message's `producer_app` is still reported as a fact about that message, but it doesn't make that app a step-4 target.

## 3. Commands: what to collect

**Collect first, assess later.** Your job here is to collect every Kafka record related to the incident. Deciding what went wrong comes afterwards (`investigator`, then the report). Collect exactly these four things for each incident topic, and nothing else:

| # | Collect | Which topics | Commands |
|---|---|---|---|
| 1 | **Incoming:** messages carrying the business key, plus consumer client logs | topics the seed app **consumes** (config `kafka.consumer.topics`, intersected with the incident's `topics=`) | offsets → console consumer; `kafka logs --component consumer` |
| 2 | **Outgoing:** messages carrying the business key, plus producer client logs | topics the seed app **produces** (config `kafka.producer.topics`, intersected with the incident's `topics=`) | offsets → console consumer; `kafka logs --component producer` |
| 3 | **Retries:** every producer send retry and consumer redelivery/retry | every incident topic | `kafka logs --component producer` and `--component consumer` (unfiltered, so no retry line is missed) |
| 4 | **Topic errors and connection timeouts:** any error, timeout, disconnect or authorization failure that names the topic or one of its partitions | every incident topic | `kafka logs --component broker`, plus the producer/consumer logs from 1–3 |

If the seed config is unavailable, direction (incoming vs. outgoing) is unknown. Collect 1 and 2 for **every** incident topic anyway, and report the direction as unknown.

**Messages by time:** first find the offsets at the window start, then read from them, once per partition.
```
mocklogs kafka-get-offsets --bootstrap-server <servers> --topic <topic> --time <epoch-ms> --save-dir <workdir>
mocklogs kafka-console-consumer --bootstrap-server <servers> --topic <topic> \
    --partition <p> --offset <o> --max-messages <n> \
    --property print.headers=true --property print.timestamp=true \
    --property print.partition=true --property print.offset=true \
    --grep <business-key-value> --save-dir <workdir>
```
- `--grep` is a mock extension (the real tool would be piped to grep).
- **A missing message is a finding too.** If no partition has the business key on a topic where one was expected, keep that empty result (it's saved with the command).
- The `producer_app` header says who produced **that message**. It doesn't add apps to investigate (only the config does). If it disagrees with the config's `upstream.apps`, report the mismatch.
- The `correlation_id` header is the **producer's own** ID. It's only valid for searching the **producer app's** logs (`incident-app-logs`), never other apps or other topics.

**Broker and client logs for a topic, by time** (one command per component per incident topic):
```
mocklogs kafka logs --bootstrap-server <servers> --component broker|producer|consumer --topic <topic> \
    --since-time=<rfc3339> --until-time=<rfc3339> --save-dir <workdir>
```
Don't filter these logs with `--grep`: retries, timeouts and errors often don't carry the business key, and dropping them would lose exactly the lines that matter. A `clientId=` in these lines is attributed to an app **only** through the seed config's `*.kafka.client.ids`.

## 5. What to collect: checklist

Before moving on, check that each incident topic has:
- [ ] **incoming** messages with the business key (or an empty result showing there are none);
- [ ] **outgoing** messages with the business key (or an empty result);
- [ ] **producer** and **consumer** client logs for the window (these hold the **retries**);
- [ ] **broker** logs for the window (these hold **topic errors** and **connection timeouts**: `TimeoutException`, `timed out`, `disconnected`, `NOT_ENOUGH_REPLICAS`, `NotLeader…`, offline partitions, authorization failures naming the topic).

You don't judge any of it. Collect it all and let `investigator` and the report do the assessment. Timing is also left to `investigator`: a message consumed about a minute after it was produced can be normal delivery delay, not clock skew.
